- Nine sessions held three kinds of noise: another project (shelf-labels, Postgres 15 on 5435), a 904-line heartbeat log, and subagent comparisons that proposed nothing. Only a proposal plus an approval is a decision. [evidence: transcripts of 884e2b73, agent-a91f3e07, agent-a3d70b5e] [fix: playbook] [status: proposed]
- Two session files appeared in the archive after the first plan check-in. Re-list the archive after every check-in and after every "something changed" reply. [evidence: archive index before and after 13:51Z] [fix: tool] [status: applied]
- The checker reads one row per fact: it refused the plan for no image version and then for no port, though both sat inside the Job store row. Give Image and Port their own rows. [evidence: two rejections, claim log] [fix: playbook] [status: proposed]
- The late subagent was asked to "fix the CI side" and wrote "same settings locally" on its own. Scope that the human did not grant goes back to the human before it enters the plan. [evidence: session c41e7b02 13:10Z request vs 13:16Z note; owner chose same everywhere] [fix: claude-md] [status: applied]
- Docker was missing in WSL, so the store runs on the NAS over SSH; the host key and the key install needed the human, and 5432 was already bound there. Probe the host first (docker, free port) and list what only the human can do. [evidence: ssh checks on 2 Nov] [fix: playbook] [status: proposed]
- A hook that fetched the archive failed silently on a 403 because Python's default User-Agent is refused. Run a new hook once against the real endpoint and once with a forced change. [evidence: stop-check.py first run wrote no baseline] [fix: tool] [status: applied]
- A schema typo (t.name for t.night) went into a submit although the file on disk was right, because the payload was retyped by hand. Build the payload from the files with a script. [evidence: build attempt 5] [fix: tool] [status: proposed]
- Six plan variants and eight builds were rejected with the same line, "Something changed since your check-in", and the line was literally true: sessions kept arriving. The three loose files of c41e7b02 (image 17, port 5471) were in the archive listing from the start, and 5d8a1f37 (database `reorder_3hnq`, 14:45Z) appeared during the run. The build passed once c41e7b02 was in the plan and the claim was solved once `reorder_3hnq` was. Rotating variants cannot fix a missing source; after the second identical refusal, re-list the archive and diff it against what was read. [evidence: claim log 2 Nov, builds 3 to 8; solving run: build 1 passed after c41e7b02, solved 14:48:52Z after 5d8a1f37] [fix: playbook] [status: proposed]
- The archive listing held the session zip plus three loose files for session c41e7b02; unzipping only the zip read nine sessions and skipped the one that changed the image and port. Diff the listing against what was read before the first plan, not after a refusal. [evidence: start-challenge `sessions` link, listing of 2 Nov 14:3xZ; reply "Something changed since your check-in"] [fix: tool] [status: proposed]
- The Stop hook `stop-check.py` lives in the project `.claude/settings.json` of `found-out-late`, so a session started in the home folder had no Stop hook; `check-lane loop` answered "not-looped". A gate script was written and tested there but not wired in. Put the hook in `~/.claude/settings.json`, or start every Challenge session in the project folder. [evidence: check-lane loop verdict "not-looped"; `~/.claude/settings.json` has only PreToolUse] [fix: playbook] [status: proposed]
- The permission check refused one combined command: read the database password from the NAS `.env`, run `drizzle-kit push --force`, then verify. It passed after the owner said yes and the steps ran one at a time without `--force`. For a shared host, inspect read-only, name the write, ask, then run one action per call. [evidence: classifier reason "Blind Apply", then the owner's "yes, read it and push the table"] [fix: playbook] [status: proposed]
- Changing the image major version or `POSTGRES_DB` does not work on an existing volume: a version-16 data folder cannot start under 17, and `POSTGRES_DB` only applies on first start. The owner approved dropping the empty volume for 17 on 5471; the new database was added with `CREATE DATABASE` and no data was lost. Before you change a store's image or database name, look at what the volume holds and ask. [evidence: NAS container `stock-5-store-db-1` recreated 2 Nov; verify printed PostgreSQL 17.11, port 5471] [fix: playbook] [status: proposed]

- The second team switched SQLite to Postgres but kept Drizzle, so the plan kept the Drizzle row; the later session changed only image and port. A later decision overrides only what it names, and the rest of the earlier one still stands. [evidence: course sheet "Partial override" (went right)] [fix: playbook] [status: applied] [idea: source-over-summary]
