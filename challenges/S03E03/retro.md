## Findings
- Agents re-explore from zero each time and leave no trail. A feature map (one short file per feature: role, how to get there, how to verify, what to keep in mind) holds only what the code does not show. Here that context lives in memory notes and scattered docs, and nothing is per feature; `mail-agent` and its `log_mismatch` history is the first candidate. [evidence: lesson "Exploration", figure 1; memory `s02e05-while-youre-away-lessons`] [fix: playbook] [status: proposed] [idea: write-down-state, package-it]
- Maps and notes rot. The lesson says a maintaining schedule must modify and archive, not only add. Nothing here checks age: the S02E05 memory note carries codes and window state that were true on 2026-11-06. A staleness pass should list docs and memory entries past an age and propose modify or archive, for the owner to approve. [evidence: lesson "Exploration", "no document is better than the wrong one"; memory note dated 4 days old] [fix: tool] [status: proposed] [idea: look-again, package-it]
- Reading the diff is not the proof. The transcript's agent proves its work with a preview, screenshots or a video, and a system recap of which primitives it composes, extends or deletes. Our CLAUDE.md already says to name a check run against the running thing; add that a screenshot or live output is attached to the claim. [evidence: transcript "screenshots... forcing the agent to verify for itself"; `mega-dev-local/CLAUDE.md` "name the check you ran"] [fix: claude-md] [status: proposed] [idea: source-over-summary, rehearse-the-shape]
- The reviewer must not be the implementer: a fresh context, ideally another model, with the implementer made to answer each comment. We have `source-reader` for single sources but no review agent separate from the author, and `/10x-impl-review` runs in the same session. [evidence: transcript "you do not want the reviewer to be the same as the implementer"; `.claude/agents/` holds only source-reader] [fix: skill] [status: proposed] [idea: human-at-fork, distrust-decoys]
- Deterministic checks beat AI review on cost and repeatability: lint, types, dead-export check, a slop ratchet and tests as one validate that blocks merge. We have `tools/check-all`, a pre-commit hook and `retro-check`; whether `check-all` is the single blocking gate, and whether agents may add ratchets for patterns they notice, is not yet decided. [evidence: transcript "npm run validate runs 33 checks"; `tools/check-all`, `hooks/pre-commit`] [fix: tool] [status: proposed] [idea: code-over-prompt]
- A skill that walks a whole flow should be a short pointer to a CLI that is a state machine: each run prints only the context for the next step, so the prompt is small and the agent is not flooded with branches it will not take. Our claim steps (`record-claim`, `pre-claim-gate`) already work this way; the next step is a CLI that prints the next step for a whole challenge. [evidence: transcript "progressive disclosure... effectively a state machine"; `tools/record-claim`] [fix: tool] [status: proposed] [idea: code-over-prompt, package-it]
- Merge by risk, not by habit. Low and medium risk may merge on green; high risk needs an explicit owner yes. This matches the existing rule that outside actions need a yes, and the `gh pr merge` reminder hook. The risk classes and who sets them are not written down. [evidence: transcript "if it's high risk, then you can only merge if Kent explicitly says"; settings.json merge reminder hook] [fix: claude-md] [status: proposed] [idea: human-at-fork]
- Research only as deep as it can be verified. Agent reach is not the limit; the owner's ability to explain, check, cross-check and sign off is. Before leaning on a new service or method, record how it will be verified. [evidence: lesson "Execution: Research", figure 5, four checks] [fix: playbook] [status: proposed] [idea: contract-first, human-at-fork]
- Schedules and feedback are part of the system. Many agents exhaust RAM, disk and CPU; the NAS runs more than thirty containers and I did not check any prune or queue. Agents also need read-only production signals (logs, errors) beyond container logs. Start with one audit and one scheduled cleanup, not a platform. [evidence: lesson "Schedules", figures 8 and 9; `docker ps` on the NAS, 2026-11-11] [fix: none] [status: proposed] [idea: write-down-state, look-again]
