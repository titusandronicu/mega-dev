# Plan: automated course checks queued in HQ, run by a pull worker (proposed, not started)

Goal: HQ shows what happened in the course (solves, status), and the owner can start or schedule a check from HQ and see whether it ran.

## Findings
- HQ has no dispatch (`context/foundation/hq.md`). `challenges` has `status` and `steps_done` but no solve time, debrief link or summary. S01E02 is still `open` in HQ because ingest is manual.
- Course tools (`mega-start`, `list-challenges`, `resume-challenge`) only work in a Claude session with the course login, which lives on the UGREEN. HQ cannot call them.
- Guardrails from `2026-10-27-tooling-split.md`: course identity stays out of bot workers; `rook` and `debrief` are never dispatched; recordings and lesson text are untrusted data.
- `service_role` has no write on `challenges`. A worker must not get broader rights than that.
- The live `mega-hq` checkout is not at `~/Dev/mega-hq-*` (those are Oct 26 snapshots). Find it before any change.

## Design: HQ holds the queue, a worker on the UGREEN pulls
HQ never connects to the worker. The worker connects out to HQ, so there is no new open port.

1. Table `runs`: `id`, `kind` (`sync-status` first), `status` (`queued`, `running`, `needs-human`, `done`, `failed`), `requested_by` (`owner-button` or `cron`), `created_at`, `started_at`, `finished_at`, `summary`, `error`.
2. Pull button: the owner screen inserts a `runs` row with `queued`. RLS: owner only.
3. Crontab on the UGREEN, two entries:
   - `*/10 * * * * tools/hq-worker`: claim one `queued` row atomically, run it, write the result.
   - `0 */6 * * * tools/hq-enqueue sync-status`: insert a scheduled run. The schedule lives in cron, not in HQ.
4. Worker runs headless `claude -p` in `mega-dev` with an allow-list of read-only tools: `mega-start`, `list-challenges`, `resume-challenge`. It denies `start-challenge`, `claim-challenge`, `debrief`, `rook`, `artifact`.
5. The model's reply is untrusted. The worker asks for JSON, validates it with the existing `ingest/map.mjs` rules, then writes through a narrow RPC (`record_run`) with its own worker token. It does not use `service_role` or the owner login.
6. Tracking: HQ shows last run, next expected run and an `overdue` flag when a job is later than 2x its interval. A run stuck in `running` past a timeout becomes `failed`.
7. `needs-human`: the worker sets it when a step needs you (a new session, a sign-in, a 403 or 429). It never retries a blocked step on its own.

## Phases
1. Solve record (small, no worker): migration adds `solved_at`, `debrief_url`, `summary` to `challenges`. Push S01E02 through ingest as solved. Rule in `CLAUDE.md`: after the debrief, record it in HQ.
2. Queue: `runs` table, `record_run` RPC, worker token, RLS, tests in the HQ repo style.
3. Worker: `tools/hq-worker` and `tools/hq-enqueue` in the HQ repo, allow-list config, lock file so two runs never overlap.
4. UI: a Runs screen with the Run button, status list, overdue flag.
5. Crontab entries, then a runbook with rollback (comment out the two cron lines; the queue stays harmless).
6. Slack (workspace `funkykovalLab`, channel `#all-funkykovalab`):
   - 6a notifications: GitHub's Slack app subscribes the channel to `mega-dev` and `mega-hq`; `hq-worker` posts one line per run (started, `done`, `failed`, `needs-human`) and a daily digest through an incoming webhook. After phase 3.
   - 6b control: `/hq run <kind>`, `/hq status`, and Approve / Retry buttons, over Socket Mode (the service connects out; no inbound port). Only the owner's Slack user ID may trigger anything, and only the same read-only kinds as the Run button. After phase 4.
   - Secrets (`SLACK_WEBHOOK_URL`, later the bot token) live in `~/.config/mega-hq/slack.env`, mode 0600. Posted text goes through the existing redaction first.

## Out of scope for now

- Anything that runs `rook` or `debrief` unattended.
